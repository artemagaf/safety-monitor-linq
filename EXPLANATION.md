# Объяснение кода: часть «модель»

Документ для того, кто отвечает за нейросеть: как устроена модель, как её обучить, перенести на LinQ
и доказать жюри, что она работает. В конце — коротко про видеоконвейер напарника и о чём с ним договориться.

## 0. Что за что отвечает

### Путь одного кадра через систему

```
камера (RTSP) / видеофайл / стоп-кадры
   │
   ▼  pipeline.py ── CameraWorker: читает кадры, по потоку на каждую камеру
   │
   ▼  backends.py ── МОДЕЛЬ: кадр -> список объектов (человек, каска, перчатка, ...)       ← ТЫ
   │
   ▼  tracker.py ─── даёт каждому человеку постоянный номер #1, #2, ...
   │
   ▼  rules.py ───── чья это перчатка? в какой зоне стоит? что здесь запрещено? -> нарушения
   │
   ▼  events.py ──── Debouncer: нарушение держится ~2 с? -> подтверждено; новое? -> ОДНА тревога
   │                 тревога: кадр-доказательство + запись в журнал (SQLite) + Telegram / webhook
   ▼  draw.py ────── рисует рамки и подписи на кадре
   │
   ▼  segments.py ── пишет кадр в текущий 5-секундный кусок
   │                 кусок набран: нарушений нет -> удалить; есть -> клип, привязанный к тревоге
   ▼
desktop/ ──────── окно диспетчера: живые камеры, лента тревог, журнал, статистика, зоны
```

## 1. Общая картина

```
 камера ──► кадр ──► [ МОДЕЛЬ ] ──► детекции ──► трекер ──► правила ──► события / веб
                     ▲  твоя зона                └──────── зона напарника ────────┘
```

Модель делает одну вещь: **по кадру возвращает список объектов** — что найдено, где (бокс), с какой
уверенностью. Решения «нарушение или нет» модель не принимает: это делают правила дальше по конвейеру.

Такое разделение важно:
- модель можно переобучить или заменить, не трогая логику нарушений;
- логику можно менять (новые зоны, новые правила), не переобучая модель;
- вам двоим нужно договориться только о **контракте** — формате `Detection` и списке классов.

### Контракт между вами

```python
@dataclass
class Detection:
    box: (x1, y1, x2, y2)   # пиксели исходного кадра
    conf: float             # уверенность 0..1
    cls: str                # имя класса из модели
```

Список классов модели:

| Класс | Что это | Как используют правила |
|---|---|---|
| `person` | человек целиком | основа: к нему привязываются все остальные объекты |
| `helmet` | каска на голове | СИЗ надето |
| `no_helmet` | голова без каски | нарушение «нет каски» |
| `vest` / `no_vest` | торс в жилете / без | нарушение «нет жилета» |
| `mask` / `no_mask` | лицо в маске / без | нарушение «нет маски» в зонах, где она нужна |
| `cigarette` | сигарета | нарушение «курение» |
| `glasses` / `no_glasses` | лицо в защитных очках / без | нарушение «нет очков» у станков, где летит стружка |
| `gloves` / `bare_hand` | рука в перчатке / голая | «нет перчаток» (лазер, листовой металл) **или** «перчатки запрещены» (токарный, сверлильный, фрезерный) |

**Почему есть отдельные классы `no_*`.** Отсутствие объекта детектор не видит: если каска не найдена,
это может значить «её нет», а может — «человек стоит спиной» или «голову закрыл кран». Класс `no_helmet`
(«видна голова, и на ней нет каски») — это прямое, положительное доказательство нарушения. Поэтому
режим по умолчанию в `config.yaml` — `ppe_mode: negative`. Режим `absence` (нарушение = каска не найдена)
оставлен для датасетов, где классов `no_*` нет.

### Станочный цех: одно и то же СИЗ бывает обязательным и запрещённым

Целевые сцены — оператор у станка: лазерная резка, токарный станок, обрабатывающий центр с ЧПУ.
Здесь главное отличие от стройки: **правило зависит от станка**.

| Рабочее место | Обязательно | Запрещено | Почему |
|---|---|---|---|
| Токарный / сверлильный / фрезерный | очки | **перчатки** | стружка летит в глаза; перчатку затягивает во вращающийся патрон вместе с рукой |
| Лазерная резка, листовой металл | перчатки | — | острые кромки листа |
| ЧПУ с закрытой дверью | — | перчатки (при открытой двери) | вращающийся шпиндель |

Поэтому модель отдельно учится видеть и `gloves`, и `bare_hand`, а решение «нарушение или нет»
принимают правила по зоне станка (`type: machine` в `config.yaml`, поля `require` и `forbid`).
Модель одна и та же для всех станков, меняется только конфиг.

Пример из присланных картинок: токарь в перчатках у патрона — это как раз нарушение `forbidden_gloves`,
а оператор лазера в перчатках — норма.

Тонкость привязки: рука оператора обычно вытянута к пульту или станку и выходит за бокс человека.
Поэтому перчатки ищем в полосе, расширенной на 50% в стороны (`ITEM_WIDEN` в `rules.py`), а не на 15%,
как каску.

## 2. `app/backends.py` — главный файл твоей части

Тут три способа запустить одну и ту же модель, и у всех одинаковый метод `detect(frame) -> list[Detection]`.

| Бэкенд | Файл модели | Где работает | Зачем |
|---|---|---|---|
| `UltralyticsBackend` | `.pt` | CPU/GPU через PyTorch | обучение, отладка, быстрый старт |
| `OnnxBackend` | `.onnx` | CPU через onnxruntime | **эталон** для сверки с LinQ; запасной режим |
| `LinqBackend` | скомпилированная модель | ускоритель LinQ | целевой продакшен-режим по ТЗ |

Остальной код не знает, какой бэкенд работает: он выбирается одной строкой `model.backend` в конфиге.

### 2.1 Как YOLO обрабатывает кадр — три этапа

```
 кадр 1280×720 BGR
   │  preprocess  (CPU)      letterbox до 640×640, BGR→RGB, /255, HWC→NCHW
   ▼
 тензор 1×3×640×640 float32
   │  _forward    (LinQ!)    сама нейросеть
   ▼
 тензор 1×(4+8)×8400         8400 «кандидатов», у каждого cx,cy,w,h + 8 оценок классов
   │  postprocess (CPU)      порог уверенности, перевод координат обратно, NMS
   ▼
 список Detection
```

Класс `YoloRawBackend` реализует `preprocess` и `postprocess`, а наследники — только `_forward`.
**Ключевая идея для LinQ:** на ускоритель переносится только `_forward`, самая тяжёлая часть
(90%+ вычислений). Пре- и постобработка — общий проверенный код, поэтому ONNX и LinQ гарантированно
обрабатываются одинаково, и любое расхождение результатов — это проблема именно ускорителя или квантования.

### 2.2 `letterbox` — подготовка кадра

Сеть принимает квадрат 640×640. Если кадр просто растянуть, люди станут «толстыми», и точность упадёт:
при обучении модель видела нормальные пропорции. Поэтому кадр уменьшается с сохранением пропорций,
а свободное место добивается серыми полосами (цвет 114 — тот же, что у ultralytics при обучении).

Функция возвращает `r` (коэффициент масштаба) и `pad` (размер полос) — они нужны, чтобы потом вернуть
боксы в координаты исходного кадра.

Пример: кадр 1280×720 → `r = 0.5`, картинка 640×360, полосы по 140 px сверху и снизу.

### 2.3 `postprocess` — разбор выхода сети

Выход YOLOv8/YOLO11 — тензор `(1, 4 + nc, 8400)`: для каждой из 8400 позиций на сетке — бокс
`(cx, cy, w, h)` и `nc` оценок классов. Шаги:

1. `scores.argmax(1)` / `scores.max(1)` — для каждого кандидата лучший класс и его уверенность.
2. Отбрасываем всё, что ниже `conf` (0.35).
3. Переводим `(cx, cy, w, h)` в углы `(x1, y1, x2, y2)`, вычитаем полосы `pad`, делим на `r` — получаем
   координаты исходного кадра. Обрезаем по краям.
4. **NMS** (Non-Maximum Suppression): один объект сеть находит несколькими соседними кандидатами.
   NMS оставляет из пересекающихся боксов (IoU > 0.5) один, с наибольшей уверенностью.
   `NMSBoxesBatched` делает это отдельно по каждому классу, чтобы каска не «погасила» человека.

Проверка в начале `postprocess` (число строк = 4 + число классов?) нужна на случай, если рантайм
ускорителя отдаёт тензор в транспонированном виде `(8400, 12)`. Ориентацию определяем по известному
числу классов, а не по тому, какая сторона длиннее: иначе при малом числе кандидатов проверка ошибается.

**Почему NMS не внутри сети.** NMS — операция с ветвлениями и переменным размером выхода. Компиляторы
ИИ-ускорителей такие операции обычно не поддерживают или выполняют медленно. Поэтому в `export.py`
стоит `nms=False`, а NMS выполняется на CPU: это быстро, около 1 мс.

### 2.4 `LinqBackend` — инференс на LinQ TPU (по SDK `tpu_framework_2026.9.45`)

Сделано по документации и примерам LinQ (`tpu_framework.pdf`, `usage_example_python_api`).
Как устроен ускоритель с точки зрения кода:

```
                        SDK tpu_framework (только Linux, Python 3.12)
 ppe_head.onnx ──► оптимизация ──► калибровка + квантование INT8 ──► компиляция TPU_H1M ──► ppe_head.tpu

                        Python API pytpu (на стенде LinQ)
 Device.list_devices() ─► Device.open(dev) ─► device.load("ppe_head.tpu") ─► program.inference()
                                                                                │
             {"images": float32 1×3×640×640}  ──► inference.sync(...) ──►  {имя_выхода: тензор}
```

Что важно знать:
- **Вход — обычный float32 NCHW 0..1**, как у ONNX. Перевод в INT8 (scaling, casting) и упаковку
  в память TPU (packing) `pytpu` делает сам по метаданным программы. Наш `preprocess` не меняется.
- **Тензоры называются так же, как в исходном ONNX** (`images`, `/model.23/cv2.0/.../Conv_output_0` …).
  Поэтому имена входа и выходов `LinqBackend` читает из `head_onnx`.
- **В примере API вызов называется `run()`, в документации SDK — `sync()`.** Поддерживаем оба.
- **Устройство, программа и сессия — контекстные менеджеры** (`with ...`). Нам они нужны на всё время
  работы, поэтому держим их в `contextlib.ExitStack` и закрываем в `close()` в обратном порядке.

**Почему модель режется на две части.** В разделе Supported models документации SDK у всех YOLO
(`yolov8n_pose`, `yolo12m`, `yolo5s`…) стоит сноска: модель обрезана перед концом головы, а остаток
выполняется в постобработке. Конец головы YOLO — это reshape, softmax DFL и декодирование боксов
с константами сетки: операции, которые ускорителю неудобны и почти ничего не стоят на CPU. Поэтому:
- **голова на TPU:** вся сеть до последних 6 свёрток Detect включительно (87 свёрток);
- **хвост на CPU** (`ppe_tail.onnx`, onnxruntime): 25 лёгких операций, доли миллисекунды.

Разрез делает `tools/compile_linq.py` (раздел 3.7) и сразу проверяет, что голова и хвост вместе
дают **бит в бит** тот же выход, что исходная модель (расхождение 0.0 на yolo11n).

**Как проверено без ускорителя.** `tests/test_linq_backend.py` подставляет вместо `pytpu` имитацию
с тем же API (`list_devices`, `open`, `load`, `inference`, `run`/`sync`), которая внутри гоняет голову
на CPU. Тест проверяет, что детекции `LinqBackend` совпадают с эталоном и что ресурсы закрываются
в правильном порядке. На настоящем TPU результаты будут чуть отличаться из-за квантования INT8:
это и меряет `compare.py`.

**Запасной режим.** Если SDK не установлен, `make_backend` пишет предупреждение и переключается
на `linq.fallback` (ONNX на CPU). Демо не сломается, даже если доступ к LinQ отвалится во время защиты.

## 3. `tools/` — конвейер работы с моделью

Порядок работы:

```
prepare_dataset ─► train ─► export ─► (компилятор LinQ) ─► compare ─► benchmark ─► demo_video
```

### 3.1 `prepare_dataset.py` — данные

**Для станочных цехов основной датасет — SH17**: 8 099 фото с производств, 17 классов, среди них
`Glasses`, `Gloves`, `Hands`, `Face`, `Head`, `Helmet`, `Safety-vest`. Скачивается с Kaggle
(`mugheesahmad/sh17-dataset-for-ppe-detection`). Лицензия CC BY-NC-SA 4.0: для хакатона подходит,
для коммерческого внедрения — нет, там понадобятся свои данные. Для касок и жилетов можно добавить
Roboflow «Construction Site Safety» и «Hard Hat Workers».

**Выведение негативных классов.** В SH17 нет классов «рука без перчатки» или «лицо без очков»:
есть просто `Hands` и `Face`, а перчатки и очки размечены отдельными боксами поверх. Скрипт
выводит негативы сам (словарь `DERIVED`):
- рука, на которой нет бокса перчатки → `bare_hand`; рука в перчатке → ничего, перчатка уже размечена;
- лицо без очков → `no_glasses`;
- голова без каски → `no_helmet`.

«На которой нет» означает, что центр бокса СИЗ не попал в бокс части тела (с запасом 25%).

Скрипт поддерживает два формата папок: Roboflow (`train/images`, `valid/images`) и SH17
(общие `images/` и `labels/` + списки `train_files.txt`, `val_files.txt`).

Готовых датасетов много, но классы в них называются по-разному. Скрипт:
- переименовывает классы по словарю `SYNONYMS` в наши 12 классов (`Hardhat` → `helmet`, `Face-guard` → `glasses`, …);
- выбрасывает ненужное (техника, конусы, обувь, инструмент);
- превращает полигоны сегментации в боксы;
- добавляет к именам файлов префикс источника, чтобы файлы из разных датасетов не перезаписали друг друга;
- **печатает таблицу числа объектов по классам**. Это аналитика для презентации, и по ней видно
  дисбаланс: например, сигарет обычно в 50 раз меньше, чем касок. Значит, по курению нужно
  добрать данные или честно сказать, что точность там ниже.

Если в новом датасете класс называется иначе, добавь строку в `SYNONYMS`. Скрипт печатает отброшенные
классы, так что пропуск будет видно.

### 3.2 `train.py` — обучение

Берём предобученную на COCO модель `yolo11n.pt` и дообучаем её на наших классах (transfer learning).
Модель уже умеет видеть людей и формы, остаётся научить её отличать каску от кепки.

Выбор размера: `n` (nano) — самая быстрая, `s` — точнее примерно на 5–8 mAP и медленнее примерно в 2–3 раза.
Для ускорителя и десятка камер разумно начать с `n`. Если на LinQ останется запас по скорости, попробуй `s`.

Параметры, которые стоит понимать:
- `patience=15` — ранняя остановка: если mAP на валидации не растёт 15 эпох, обучение прекращается;
- `close_mosaic=10` — mosaic-аугментация (склейка 4 картинок) полезна, но не похожа на реальную камеру,
  поэтому на последних 10 эпохах её выключаем;
- `hsv_v=0.5` — сильнее меняем яркость: в цехах бывают тёмные углы и пересвеченные проёмы.

После обучения скрипт считает метрики на test и печатает таблицу по классам:
- **P (precision)** — какая доля найденного верна (мало ложных тревог);
- **R (recall)** — какую долю реальных объектов нашли (мало пропусков). Для безопасности важнее R:
  пропущенное нарушение хуже ложной тревоги, тем более что ложные тревоги дальше гасит сглаживание;
- **mAP50** — главная сводная метрика: средняя точность при совпадении боксов по IoU ≥ 0.5.

Обучать лучше на GPU: Google Colab или Kaggle бесплатно дают T4. На CPU 50 эпох займут много часов.

### 3.3 `export.py` — перенос в ONNX

- `dynamic=False, batch=1` — фиксированный размер входа. Ускорители компилируют сеть под конкретные
  формы тензоров, динамические размеры они обычно не поддерживают.
- `opset=12` — консервативная версия набора операций ONNX; её поддерживает большинство компиляторов.
- `simplify=True` — упрощение графа (сворачивание констант, удаление лишних узлов).
- `--calib-from ... --calib 200` — копирует 200 случайных картинок из val в `models/calib/`.
  При квантовании в INT8 компилятор прогоняет их через сеть, чтобы подобрать диапазоны значений.
  Калибровочные картинки должны быть похожи на реальные кадры: поэтому берём их из val, а не случайные.

Скрипт печатает формы входа и выхода. Их стоит записать: они пригодятся при подключении LinQ.

### 3.4 `compare.py` — доказательство, что LinQ работает правильно

Прогоняет одни и те же картинки через эталон (ONNX на CPU) и проверяемый бэкенд (LinQ), сопоставляет
детекции одного класса по IoU и считает:
- **recall** — какая доля детекций эталона нашлась у LinQ;
- **precision** — какая доля детекций LinQ есть у эталона;
- средний IoU боксов и разницу уверенности.

Квантование в INT8 немного сдвигает числа, поэтому идеального совпадения не будет. Порог «OK» — 95%.
Если совпадение сильно ниже, причина почти всегда одна из трёх: другая нормализация входа
(0..1 против 0..255), RGB против BGR или неправильная деквантизация выхода.

Эту же проверку стоит сделать для пары `.pt` против `.onnx`, чтобы убедиться, что экспорт ничего не сломал.

### 3.5 `benchmark.py` — цифры для презентации

Делает 10 прогревочных прогонов (первые всегда медленные), затем 100 замеров. Печатает:
- **Сеть, мс** — только `_forward`. Здесь видно ускорение именно от LinQ;
- **Всего, мс** — с пре- и постобработкой: столько реально занимает один кадр;
- **p95** — 95-й процентиль задержки. Он важнее среднего для «реального времени»: показывает, насколько
  плохо бывает в худших случаях;
- **FPS** — сколько кадров в секунду тянет один поток. Сколько камер выдержит система: FPS ÷ частота
  анализа на камеру (10 кадров/с в конфиге).

В конце скрипт печатает markdown-таблицу. Прогони его для `onnx` и `linq`, и таблица сравнения CPU и LinQ
готова для слайда.

Точка отсчёта, замерено на твоём ноутбуке (i5-12450H, CPU, `yolo11n`, вход 640):

| Бэкенд | Сеть, мс | Всего, мс | p95 | FPS |
|---|---|---|---|---|
| ultralytics (.pt) | — | 118.8 | 128.6 | 8.4 |
| onnx (.onnx) | 70.2 | 78.8 | 86.3 | 12.7 |

Пре- и постобработка занимают около 9 мс из 79. Значит, почти всё время уходит на сеть, и именно её
ускоряет LinQ.

### 3.7 `compile_linq.py` — из ONNX в программу для LinQ TPU

```bash
python tools/compile_linq.py split   --onnx models/ppe.onnx                                    # любая ОС
python tools/compile_linq.py compile --onnx models/ppe.onnx --calib-dir datasets/ppe/val/images # Linux + SDK
```

Что делает:
1. **`split`** — находит 6 последних свёрток головы Detect (Conv последнего модуля, выход которой идёт
   в Reshape; DFL-свёртку пропускает), режет модель на `*_head.onnx` и `*_tail.onnx`, переносит в обе
   части имена классов и проверяет на картинке, что голова и хвост вместе дают тот же выход.
2. **`compile`** — по образцу `compile.py` из SDK:
   - `preliminary_model_conditioning` — подготовка графа;
   - `RegularModel.calibrate_torch` — подбор порогов квантования. **Отличие от примера SDK:** там
     калибровка идёт на случайном шуме (`np.random.rand`), и пример сам предупреждает, что нужны реальные
     данные. У нас — 200 реальных кадров, подготовленных **нашим же `preprocess`**. Если калибровать
     на другой подготовке, пороги будут неверными и точность на TPU упадёт;
   - `quantize` → `Network.from_quantized_model` → `compiler.compile_(TPU_H1M, …, O1)` → `ppe_head.tpu`.
   - `--preset o5` быстрее, но, по документации, «может не скомпилироваться» — тогда назад на `o1`.
   - `--percentile 99.9` — устойчивость к выбросам: по документации, на больших калибровочных наборах
     max-калибровка часто квантует хуже.

3. **Проверка INT8 на CPU** (`--check 50`) — точность после квантования ещё до стенда. SDK умеет
   выполнять квантованную модель на CPU (`QuantizedModel.as_torch_graph`, раздел End-To-End Test
   документации): это та же целочисленная арифметика, что на TPU. Голова INT8 + хвост сравниваются
   с исходной моделью FP32 через `compare.match`. Выходы головы раскладываются по входам хвоста по форме
   тензора: у каждого из 6 выходов она своя. Если проверка не удалась, `.tpu` всё равно уже собран,
   а точность проверим на стенде.

**Где компилировать.** Пакеты SDK собраны только под **Linux x86_64 + Python 3.12** (`cp312-linux_x86_64`),
на Windows они не встанут. Варианты:
- **Google Colab — готовый ноутбук [`notebooks/linq_compile_colab.ipynb`](notebooks/linq_compile_colab.ipynb)**
  (раздел 3.8);
- **WSL** (Ubuntu 24.04 уже с Python 3.12): `wsl --install -d Ubuntu-24.04` в PowerShell от администратора,
  потом перезагрузка;
- компьютер напарника с Ubuntu (там же инструкция по OpenVPN для Ubuntu);
- попробовать в терминале Jupyter на стенде LinQ, если там Python 3.12.

**Если компиляция падает на блоке внимания.** В backbone YOLO11 есть блок внимания C2PSA (MatMul,
Softmax). `yolo12m` с вниманием в списке поддерживаемых моделей есть, так что, скорее всего, пройдёт.
Если нет — обучить на **YOLOv8n** (`--model yolov8n.pt` в `train.py`): там внимания нет, и
`yolov8n_pose` в списке поддерживаемых тоже есть.

**Запуск на стенде LinQ** (VPN → Jupyter `http://hackathon.lin-q.ru/`):
1. Загрузить папку проекта, `ppe_head.tpu` скопировать в `/auto/cache/<ЛОГИН>/`.
2. В `config.yaml`: `model.backend: linq`, `linq.model_path: /auto/cache/<ЛОГИН>/ppe_head.tpu`.
3. Сверка с эталоном: `python tools/compare.py --images <кадры> --ref onnx:models/ppe.onnx --test linq`
4. Замер скорости: `python tools/benchmark.py --image data/sample.jpg --backend onnx:models/ppe.onnx --backend linq`

## 4. Видеоконвейер (часть напарника) — что важно знать тебе

Код в `app/` (кроме `backends.py`) — рабочий пример того, как конвейер использует модель.
Напарник может взять его за основу или переписать.

- **`tracker.py`** даёт каждому человеку постоянный номер: сопоставляет боксы соседних кадров по IoU.
  Без этого нельзя сказать «человек №3 уже 2 секунды без каски».
- **`rules.py`** привязывает предметы к людям: каска относится к человеку, если её центр попал
  в верхние 35% его бокса. Отсюда требование к датасету: **бокс `person` должен охватывать человека
  целиком, с головой**, иначе привязка не сработает. Опасная зона проверяется по точке ног
  (низ бокса): именно она показывает, где человек стоит на полу.
- **`events.py` / `Debouncer`** — сглаживание. Событие создаётся, только если нарушение видно
  в 60% из последних 15 кадров, примерно 1,5 секунды. Это гасит единичные ошибки модели. Поэтому
  модели можно позволить порог `conf` пониже (выше recall): случайные ложные срабатывания отфильтруются.
- **`segments.py`** — запись кусками по 5 секунд (подробно в разделе 5).
- Одна модель обслуживает все камеры по очереди (`backend_lock`). Если SDK LinQ позволяет загрузить
  несколько копий модели или батч из нескольких кадров, это следующее ускорение.

## 5. Запись кусками по 5 секунд (`app/segments.py`)

Система не хранит всё видео подряд и не создаёт событие на каждый кадр. Она работает циклом:

```
 ┌─► пишем 5 с видео во временный файл (модель анализирует кадры по ходу записи)
 │        │
 │        ▼  5 с набрано
 │   были подтверждённые нарушения ≥ 1 с?
 │      ├─ нет ─► файл удаляется
 │      └─ да  ─► файл сохраняется как клип + запись в базе (место, время, кто, что)
 └────────┘  начинаем следующий кусок
```

### Почему так, а не «накопить 5 секунд и потом проверить»

- **Память.** Кадры не копятся в оперативной памяти: 5 секунд Full HD — это сотни мегабайт на камеру.
  Каждый кадр сразу дописывается во временный `.mp4` на диске, в памяти лежит только один кадр-превью.
- **Нет задержки.** Модель смотрит кадры по ходу записи, поэтому к концу куска решение уже готово
  и нет паузы на «проверку пяти секунд разом».
- **Решение принимается по куску.** Решение «сохранить или удалить» принимается по 5 секундам целиком,
  а не по отдельному кадру.

### Что считается нарушением в куске

Берутся только **подтверждённые** нарушения, прошедшие сглаживание `Debouncer` (60% из 15 кадров).
Случайная ошибка модели на одном кадре кусок не сохранит. Плюс порог `min_violation_sec: 1.0`:
нарушение должно быть видно в куске хотя бы 1 секунду. Иначе хвост в 0.1 с на стыке двух кусков
сохранял бы почти пустой клип, а само нарушение уже есть в соседнем.

Пока нарушение длится, сохраняется каждый его 5-секундный кусок: так видно, сколько оно продолжалось.
А уведомление в Telegram или webhook уходит один раз, не чаще `cooldown_sec` (30 с).

### Что запоминается о месте работ

Каждый сохранённый клип — это строка в таблице `incidents` (`data/incidents.db`):

| Поле | Пример | Откуда |
|---|---|---|
| `place` | «Цех №1, участок штамповки» | `place` камеры в `config.yaml` |
| `t_start`, `t_end` | время начала и конца куска | часы сервера |
| `clip`, `snapshot` | `cam1_20261021_183921_974.mp4` / `.jpg` | файлы в `data/clips/` |
| `violations` | список нарушений, см. ниже | правила |

Для каждого нарушения внутри клипа: тип («Нет каски»), номер человека, **зоны, в которых он стоял**
(«Покрасочный участок»), **точка в кадре** (`pos`, доли 0..1: где именно на участке), бокс,
когда впервые замечено и сколько кадров длилось. Превью — кадр, на котором нарушений больше всего.

### Чтобы не забился диск

- Чистые куски удаляются сразу. На диске живёт один временный файл на камеру.
- `max_total_mb: 2048` — лимит папки с клипами. При превышении удаляются **самые старые** клипы,
  а запись об инциденте в базе остаётся (поле `clip` становится пустым): история нарушений не теряется.
- Недописанные временные куски после аварийного выключения удаляются при следующем запуске.

### Тонкость с частотой кадров

Длина куска считается в проанализированных кадрах: `5 с × частота анализа`. Для видеофайла фактическая
частота анализа — частота файла, делённая на шаг. Например, 25 кадров/с при шаге 2 дают 12.5, а не 10
из конфига. Поэтому `_run_file` пересчитывает её через `recorder.set_fps()`: иначе куски получались бы
по 4 секунды, а клипы проигрывались бы ускоренно.

## 6. Десктопное приложение «Пост контроля ОТ»

```bash
python run_desktop.py
```

Кейс разрешает «веб-интерфейс или локальный GUI». Выбрали десктоп: видео с камер не уходит в интернет,
приложение работает внутри контура предприятия рядом с ускорителем.

**Как устроено.** Ядро (`app/`) не знает про интерфейс. `Runtime` запускает по потоку `CameraWorker`
на каждую камеру. Окно раз в 0,1 с забирает у каждого потока последний размеченный кадр
(`latest_frame`), а раз в секунду спрашивает у журнала новые тревоги (`store.alerts(after_id=…)`).
Ядро и окно общаются только через эти два места, поэтому окно не тормозит обработку, а ядро
можно запускать и без окна (`tools/demo_video.py`).

**Как разделы закрывают требования кейса:**

| Требование кейса | Где в приложении |
|---|---|
| приём видеопотоков или наборов изображений (имитация стоп-кадров) | источник камеры: `rtsp://…`, видеофайл, картинка или папка картинок |
| оперативное оповещение: кадр или фрагмент видео, камера, время, тип | лента тревог: кадр, клип 5 с, участок, зона, номер человека, время; мигание на панели задач и звук для критичных |
| одно нарушение — одно оповещение | `Debouncer`: пока нарушение длится, повторов нет; новая тревога — только после перерыва |
| журнал с фильтрами по типу, камере, зоне, времени | раздел «Журнал» + выгрузка в CSV |
| настройка правил и зон для каждой камеры (желательно: полигон на кадре) | раздел «Зоны и правила»: точки мышью, «обязательно / запрещено», применяется сразу |
| подтверждение или отклонение оператором для дообучения | кнопки «Подтвердить / Мастеру / Ложное»; ложное → исходный кадр в `data/retrain/` |
| дашборд: нарушения по типам, камерам, времени суток | раздел «Статистика»: тепловая карта «камера × час» |
| несколько потоков одновременно; замеры скорости | по потоку на камеру; раздел «Производительность»: к/с и мс по камерам, замер модели |

**Камера без сигнала.** В конфиге есть сетевая камера склада, которой нет. Плитка показывает
«нет сигнала», поток каждые 2 секунды пытается переподключиться, остальные камеры работают.
На защите это наглядно показывает отказоустойчивость.

**Почему кадры показываются через OpenCV, а не через видеомодуль Qt.** Кадр всё равно уже есть
в памяти: его прочитал и разметил конвейер. Видеомодуль Qt потребовал бы отдельный поток чтения
того же видео и тяжёлые дополнительные пакеты. Клипы проигрываются так же: OpenCV читает mp4,
Qt показывает кадры.

## 7. Обученная модель и гибрид

**Обучение.** YOLO11n дообучена на датасете Construction-PPE (Ultralytics, 1416 фото, лицензия AGPL-3.0),
40 эпох на процессоре ноутбука (i5-12450H), около 3,5 часов. Веса — `models/ppe.pt`, для LinQ — `models/ppe.onnx`.

Качество на отложенной выборке test (141 фото):

| Класс | Точность P | Полнота R | mAP50 |
|---|---|---|---|
| person | 0.77 | 0.82 | 0.85 |
| helmet | 0.89 | 0.92 | 0.94 |
| vest | 0.80 | 0.90 | 0.92 |
| glasses | 0.66 | 0.81 | 0.83 |
| gloves | 0.78 | 0.75 | 0.77 |
| no_helmet | 0.35 | 0.28 | 0.26 |
| no_glasses | 0.25 | 0.27 | 0.17 |
| bare_hand | 0.29 | 0.17 | 0.17 |
| **все** | | | **0.61** |

Видно главное: **то, что есть (каска, жилет, очки, перчатки), модель находит хорошо; «отсутствие»
(`no_*`, голая рука) — плохо.** Примеров «без каски» в датасете в 3–4 раза меньше, и отличить голову без
каски от головы в кепке сложнее. Поэтому в `config.yaml` очки и каски проверяются через сравнение
«надето / не надето», а критичное правило станков (перчатки запрещены) опирается на класс «перчатки» —
он надёжный.

**Разрыв доменов и гибрид.** Датасет снят на стройках. На кадрах из станочного цеха обученная модель
нашла людей, но перчатки токаря у патрона пропустила, а кепку приняла за каску. Поэтому в приложении
работает **составной бэкенд** (`CompositeBackend`, `backend: composite` в конфиге):

| Часть | Модель | Отвечает за |
|---|---|---|
| 1 | `ppe.pt` — наша обученная YOLO11n | люди, каски, жилеты, очки |
| 2 | `world_hands.pt` — YOLO-World с классами, зафиксированными заранее | перчатка / голая рука |

YOLO-World — детектор с открытым словарём: классы задаются словами (`glove`, `bare hand`), а не обучением.
Классы зафиксированы один раз (`set_classes` → `save`), поэтому при работе текстовая модель CLIP не нужна:
это обычный детектор YOLO, его так же можно экспортировать в ONNX и скомпилировать для LinQ.
На кадрах станочного цеха: перчатки токаря — 0,84, перчатка оператора лазера — 0,59, голая рука на ЧПУ.

**Что сказать жюри честно.** Своих размеченных кадров станочного цеха у нас нет. Дальнейший путь — кнопка
«Ложное» в приложении: такие кадры копятся в `data/retrain/`, их размечают и дообучают модель на своём цехе.
Тогда вторая модель станет не нужна.

## 8. Поведение во времени: падение, бег, телефон, техника

Задача №1 кейса — поведенческие паттерны. Сделаны четыре сценария, **без дополнительного обучения**:

| Сценарий | Как распознаём | Модель | Где в коде |
|---|---|---|---|
| **Падение, лежит неподвижно** (критичное) | рамка человека шире высоты — кандидат; модель позы проверяет линию «плечи — бёдра»: горизонтальна → лежит; лежит дольше `fall_sec` (3 с) → тревога. Бёдер не видно (сидит за пультом) — не падение | YOLO11n-pose (17 точек скелета) | `app/behavior.py` |
| **Бег по цеху** | скорость центра человека за 1 с, в ростах человека в секунду; быстрее `run_speed` (1,5) → бег. Рост из высоты рамки — порог не зависит от расстояния до камеры | трекер | `app/behavior.py` |
| **Телефон** у станка или в цеху | телефон привязан к человеку (руки или голова); у камеры или зоны стоит `forbid: [phone]` | YOLO11n COCO (`cell phone`) | `app/rules.py` |
| **Опасное сближение с техникой** (критичное) | зазор между рамкой человека и машины меньше `vehicle_gap` (0,3) роста человека | YOLO11n COCO (`car`, `truck`, `bus`, `motorcycle`) | `app/rules.py` |

Модели в приложении работают вместе (`backend: composite`): обученная `ppe.pt` (СИЗ), `world_hands.pt`
(руки) и стандартная `yolo11n.pt` (телефон, техника и люди в любой позе: обученная модель лежащих
не видит — она училась на стоящих). Одинаковые объекты от разных моделей объединяются. Модель позы
вызывается только для «широких» рамок, то есть почти никогда.

**Две доработки трекера, без которых бег не работал:**
- при 2 кадрах в секунду бегущий смещается больше своей ширины, рамки соседних кадров не пересекаются.
  Трекер теперь сопоставляет людей ещё и по расстоянию (меньше 1,5 роста);
- скорость для видеофайла считается по времени в ролике, а не по часам: если процессор не успевает,
  ролик проигрывается медленнее, а скорость по часам вышла бы заниженной.

**Проверка.** Демо-ролик `data/scenarios.mp4` (`tools/make_scenarios_video.py`) — камера «Сценарии
поведения» в приложении. Прогон через конвейер даёт: 3 тревоги «сближение с техникой» (люди у автобуса),
«бег», «падение», «телефон». На камерах лазера и ЧПУ ложных тревог нет. Плюс тесты в
`tests/test_pipeline_logic.py`.

**Честно для жюри:** ролик — постановка из фотографий (бегущий — вырезанный и перемещаемый человек,
лежащий — повёрнутое фото), своих видео происшествий у нас нет. Для проверки на реальных падениях
подойдёт датасет SAFER-Activities (падение, бег, лежание с разметкой по времени). Погрузчика в COCO нет —
для склада технику нужно дообучать.

**Скорость.** Три модели на пять камер на процессоре ноутбука — около 0,5 кадра в секунду на камеру.
Для реального времени нужен ускоритель (LinQ) или меньше камер на один компьютер.

## 8.1 Открытый огонь и переноска грузов

| Сценарий | Как распознаём | Модель | Где в коде |
|---|---|---|---|
| **Открытый огонь** (критичное) | CLIP сравнивает кадр и его 4 четверти с подписями «пламя, костёр, дым» и «цех, лампа, сварочные искры». Вероятность «огонь» ≥ 0,8 → огонь, рамка — та четверть. Это **нарушение места**: тревога идёт и без людей в кадре (номер 0, в карточке «место, без человека») | CLIP ViT-B/32, без обучения | `app/fire.py`, `app/rules.py` |
| **Груз закрывает обзор** | коробка касается верхней четверти тела (несёт перед лицом или над головой) | YOLO-World («cardboard box») | `app/rules.py` (`unsafe_carry`) |
| **Подъём груза спиной** | по скелету: туловище наклонено ≥ 55° от вертикали, а колени почти прямые (сгиб ≤ 40°) дольше 1 с. Правильно — присесть, спина прямая, поднимать ногами, груз у пояса: тревоги нет | YOLO11n-pose | `app/behavior.py` (`bent_lift`) |

**Почему огонь через CLIP, а не YOLO.** В датасетах СИЗ огня нет, а YOLO-World по слову «fire» не нашла
пламя даже на фото костра. CLIP обучен на сотнях миллионов пар «картинка — подпись» и узнаёт пламя без
дообучения: на кострах вероятность 0,99–1,00, на кадрах цеха, станков, SH17 и на рисунках — не выше 0,26.
Подписи «сварочные искры» и «лампа» добавлены как «не огонь», чтобы сварка не давала ложных тревог.
CLIP медленнее YOLO (~0,25 с на кадр), поэтому проверяем раз в секунду и держим результат между проверками.

**Как правильно переносить груз (что проверяем и что нет).** Правила: присесть, а не наклоняться; спина
прямая; поднимать усилием ног; груз держать близко к телу на уровне пояса; не закрывать грузом обзор;
не поворачивать корпус с грузом. Камера проверяет наклон спины, сгиб колен и положение груза относительно
головы. Вес груза и поворот корпуса камера не измеряет. `lift_needs_load: true` — тревога «подъём спиной»
только при найденном рядом грузе (меньше ложных тревог, но коробку на полу модель видит не всегда).

**Согнулся ≠ упал.** У согнувшегося рамка тоже широкая и туловище почти горизонтально, поэтому «лежит»
теперь требует ещё и горизонтальных ног: если лодыжки заметно ниже бёдер — человек стоит согнувшись.

**Проверка** — камера «Сценарии: огонь и груз» (`data/scenarios2`, кадры выбираются ◀ ▶), прогон через конвейер:

| Кадр | Результат |
|---|---|
| 1, 2 — огонь, людей нет | «Открытый огонь» (вероятность 0,99–1,00) |
| 3 — правильный подъём: присед, спина прямая, коробка у груди | тревог нет |
| 4 — рабочий поднимает камень лопатой, согнувшись на прямых ногах (наклон 68°) | «Подъём груза с наклоном спины» |
| 5 — стоит прямо со штангой | тревог нет |
| 6 — рабочий у арматуры, согнулся на прямых ногах (62°) | «Подъём груза с наклоном спины» |
| 7 — укладчик блоков присел (наклон ~50°, колени согнуты) | тревог нет |

Порог 55° выбран по датасету Construction-PPE (1328 фото, поиск моделью позы): явные наклоны — 62–88°,
пограничные (присел, частично закрыт) — 48–50°. Фото 4, 6, 7 — из Construction-PPE. Плюс тесты `test_bent_lift_vs_squat`, `test_bent_lift_needs_load_when_configured`
и огонь без людей в `test_open_fire_climbing_height_and_carry`.

## 9. Автоматические отчёты (Claude)

Раздел «Отчёты» в приложении, код — `app/reports.py`. Это пункт «автоматическая отчётность с помощью
языковых моделей» из направлений развития кейса.

1. `collect()` собирает из журнала сводку за период: всего, критичных, по типам, участкам, часам, зонам,
   статусам оператора и список событий.
2. `claude_report()` отправляет сводку в **Claude Opus 5.5** через официальный SDK `anthropic`. Системный
   промпт задаёт роль (помощник инженера по ОТ), запрет додумывать и структуру отчёта: итоги, критичные
   инциденты, проблемные участки и время, качество срабатываний, рекомендации с привязкой к цифрам.
   Включён серверный запасной режим (`fallbacks="default"`): если модель откажет по соображениям
   безопасности, API сам повторит запрос на запасной модели.
3. Нет ключа, нет сети или ошибка API — `template_report()` строит отчёт по шаблону. Сводка нужна службе ОТ
   в любом случае.

**Ключ.** Приложение само читает ключ из файла `reports.credentials_file` (по умолчанию
`iishka_credentials.json` на рабочем столе; путь к рабочему столу берётся из реестра Windows). Ключ
не хранится в коде, не пишется в логи и не попадает в архив проекта.

**Что уходит наружу.** Только сводные цифры и список событий: время, тип, участок, зона, статус.
Кадры, клипы и данные о людях не отправляются, люди в журнале обезличены (номер трека).

**Проверка.** `tests/test_reports.py`: форматы файла с ключом, сводка за период, параметры запроса к
Claude (модель, запасной режим, что кадры не уходят) — на имитации клиента, без сети и настоящего ключа.

## 10. Что сказать жюри про модель (тезисы)

1. **Инференс на LinQ, логика на CPU.** На ускоритель переносится только сеть, а пре- и постобработка
   общие и протестированы. Поэтому корректность переноса доказывается сверкой с ONNX (цифры из `compare.py`).
2. **Классы `no_*`** — модель ищет доказательство нарушения, а не отсутствие объекта. Меньше ложных
   тревог от людей, стоящих спиной.
3. **Сглаживание во времени** — событие только при устойчивом нарушении (≈1,5 с), повтор не чаще
   раза в 30 с.
4. **Цифры:** mAP по классам из `train.py`, мс/кадр и FPS на CPU и на LinQ из `benchmark.py`,
   совпадение LinQ с эталоном из `compare.py`.
5. **Отказоустойчивость:** если ускоритель недоступен, система автоматически продолжает работать на CPU.
6. **Экономия хранилища:** хранятся только 5-секундные клипы с нарушениями и местом работ.
   Чистое видео удаляется сразу, объём папки ограничен.
